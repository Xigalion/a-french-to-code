# PostgreSQL 18 comme référence, SQL standard comme priorité

**19 novembre 2026. Rien n'est implémenté.**

Deux choses sont demandées en même temps, et elles ne disent pas la même : un
**dialecte de référence** — PostgreSQL — et une **priorité au SQL standard**.
Ce document dit comment les tenir ensemble sans mentir à l'apprenant.

---

## 1. La règle de départage

> **SQL-A écrit la forme du standard chaque fois que PostgreSQL l'accepte, et
> refuse nommément la forme propre à PostgreSQL quand une forme standard
> existe.**

PostgreSQL est donc le **vérificateur**, pas le modèle. Il sert à prouver que
ce que SQL-A écrit s'exécute ; il ne sert pas à décider quoi écrire.

Ce choix a un coût, et il faut le dire : l'apprenant verra `FETCH FIRST 3 ROWS
ONLY` là où tous les exemples d'Internet écrivent `LIMIT 3`. C'est un
inconfort immédiat contre une compétence transférable. **C'est une décision de
périmètre** : décision **S6**.

## 2. Les divergences, vérifiées dans la documentation de PostgreSQL 18

| Besoin | Forme **standard**, écrite par SQL-A | Forme PostgreSQL, **refusée** | Vérifié |
|---|---|---|---|
| limiter les lignes | `FETCH FIRST n ROWS ONLY` | `LIMIT n` | **oui** — la documentation qualifie `LIMIT`/`OFFSET` de « PostgreSQL-specific syntax, also used by MySQL », et rappelle que SQL:2008 a introduit `OFFSET … FETCH` |
| décaler | `OFFSET n ROWS` | `OFFSET n` | **oui**, les deux sont acceptées ; le standard exige `OFFSET` **avant** `FETCH`, PostgreSQL accepte les deux ordres — SQL-A suivra le standard |
| clé engendrée | `ALTER COLUMN c ADD GENERATED BY DEFAULT AS IDENTITY` | `serial` | **oui**, la syntaxe figure telle quelle dans `ALTER TABLE`, avec un exemple identique |
| transtypage | `CAST(x AS integer)` | `x::integer` | oui, les deux existent |
| texte de longueur libre | `varchar(n)` | `text` | oui, `text` n'est pas un type du standard |
| ouvrir une transaction | `START TRANSACTION` | `BEGIN` | oui |
| comparaison insensible à la casse | `LOWER(c) LIKE '…'` | `ILIKE` | oui |
| renvoyer les lignes modifiées | *rien* | `RETURNING` | oui, hors standard |
| insérer sans doublon | *rien* | `ON CONFLICT` | oui, hors standard |

Les refus correspondants portent chacun un code et nomment la forme qui
enseigne la même compétence :
[`CATALOGUE_SQL_SPEC.md`](CATALOGUE_SQL_SPEC.md), section « refus de dialecte ».

## 3. Deux pièges du langage, vérifiés, qui changent le produit

### 3.1 La casse des identifiants — et le standard dit l'inverse de PostgreSQL

Documentation de PostgreSQL, mot pour mot :

> « Quoting an identifier also makes it case-sensitive, whereas unquoted names
> are always folded to lower case. »

> « The folding of unquoted names to lower case in PostgreSQL is incompatible
> with the SQL standard, which says that unquoted names should be folded to
> **upper** case. »

Donc `Eleves`, `eleves` et `ELEVES` désignent la **même** table, mais
`"Eleves"` en désigne une **autre** — et le repliement va vers le bas chez
PostgreSQL, vers le haut dans le standard.

**Décision de rendu :** SQL-A écrit l'identifiant **tel que donné** et ne le
met **jamais** entre guillemets. Mettre des guillemets « pour être sûr »
rendrait les identifiants sensibles à la casse à l'insu de l'apprenant, et
c'est exactement le genre d'ajout implicite que la règle 3 interdit.
L'information passive `SQL_IDENTIFIANT_REPLIE` l'explique à l'endroit où ça
compte.

### 3.2 Une apostrophe dans un texte se **double**

> « A literal single-quote […] write two adjacent single quotes. »

Conséquence immédiate, et c'est un vrai point de conception : la phrase

    Insère dans la table clients une ligne dont nom vaut le texte "O'Brien".

doit produire

```sql
-- Insère dans la table clients une ligne dont nom vaut le texte "O'Brien".
INSERT INTO clients (nom)
VALUES ('O''Brien');
```

Le commentaire de traçabilité garde l'apostrophe **telle que tapée** — règle 2,
la phrase exacte — tandis que le littéral la **double**. Les deux lignes
diffèrent donc à l'œil, et c'est **correct** : l'une est la phrase, l'autre est
son encodage.

**Ce n'est pas une invention au sens de la règle 3** : doubler l'apostrophe ne
change pas la valeur, c'est la seule façon de l'écrire. C'est la même nature
que `\n` dans `printf`. Mais cela doit être **décidé** plutôt que subi, et une
information passive doit le dire, sinon l'apprenant croira à une faute de
frappe. C'est la **décision S7**.

## 4. Ce que PostgreSQL impose à la validation

| Contrainte | Conséquence pour la validation |
|---|---|
| une instruction n'a de sens que **jouée contre des données** | l'exercice de clôture doit livrer un **schéma**, des **données de départ** et des **résultats calculés à la main** |
| un serveur est un **processus**, pas un compilateur | il faut un amas (`initdb`), un port, un démarrage et un arrêt — et donc une autorisation externe |
| `psql` lit un fichier avec `-f` et renvoie un code de sortie | la preuve est de la même nature que `gcc` puis exécution : code 0 **et** sortie conforme |
| `ON_ERROR_STOP=1` | sans ce réglage, `psql` continue après une erreur et **renvoie 0** : un script faux passerait pour bon |
| l'encodage | la base doit être en `UTF8`, et le client aussi — la phase 3 a perdu une demi-journée sur `javac` sans `-encoding UTF-8` |

`ON_ERROR_STOP=1` est la leçon de `javac`, transposée : **un outil qui
continue après une erreur et renvoie zéro transforme une suite de preuves en
décoration.**

## 5. Ce que ce document NE prouve pas

Tout ce qui est marqué « vérifié » ci-dessus l'est **dans la documentation
officielle de PostgreSQL 18**, pas par exécution. Aucun serveur n'est
installé ; aucune des 91 formulations proposées n'a jamais été jouée.

**La documentation dit ce que le serveur devrait faire ; seule l'exécution dit
ce qu'il fait.** La distinction n'est pas une précaution de style : la phase 3
a livré un `catch` qui écrivait deux accolades fermantes et que seule la
compilation d'un programme entier a révélé.
