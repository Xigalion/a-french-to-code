# PostgreSQL portable, et ce qu'il a déjà prouvé — 19 novembre 2026

Autorisé par le fondateur le 19 novembre 2026. **Installé, démarré, et les
affirmations de la phase 4 sont désormais vérifiées par exécution** — plus
seulement par lecture de la documentation.

L'outil n'est pas le sujet. Ce qui compte est à la §4 : **l'exécution a trouvé
un défaut du catalogue proposé.**

---

## 1. Ce qui a été installé

| | |
|---|---|
| version | **PostgreSQL 18.7**, binaires Windows x86-64 officiels |
| source | l'archive liée par `postgresql.org/download/windows` (« zip archive … without the installer »), hébergée par EDB |
| taille | 389 515 503 octets |
| `sha256` de l'archive | `ead0bbc27fb678fa24dcf86b738981323042abd073c744103bf7f3aed23f9a33` |
| emplacement | **hors du dépôt**, dossier **frère**, localisé par chemin **relatif** (`scripts/postgres.mjs`) |
| `PATH` système | **inchangé** |
| service Windows | **aucun** — le serveur est lancé par `pg_ctl`, à la demande |
| port | **55432**, non standard |
| écoute | **`127.0.0.1` seulement** |

Le port non standard n'est pas une coquetterie : `5432` appartiendrait à une
installation réelle de la machine, et s'y connecter par mégarde ferait jouer
des instructions **destructrices** sur les données de quelqu'un.

## 2. L'intégrité — et un écart honnête avec la phase 3

Temurin publiait un `sha256` officiel, et il a été **comparé**. **PostgreSQL
n'en publie aucun** : ni la page de téléchargement Windows de
`postgresql.org`, ni la page des binaires d'EDB ne mentionnent de somme de
contrôle ou de signature pour l'archive. Vérifié sur les deux pages.

Annoncer « sha256 conforme » comme à la phase 3 serait donc **faux**. Ce qui a
été fait à la place, par ordre de force :

**1. la signature Authenticode des binaires extraits — vérifiée :**

```
postgres.exe   Valid   CN=EnterpriseDB Corporation, O=EnterpriseDB Corporation, …
psql.exe       Valid   CN=EnterpriseDB Corporation, …
initdb.exe     Valid   CN=EnterpriseDB Corporation, …
pg_ctl.exe     Valid   CN=EnterpriseDB Corporation, …
```

C'est **plus fort** qu'un hachage publié sur la même page que le fichier :
un attaquant qui tient la page tiendrait aussi le hachage, alors qu'il ne
tient pas la clé de signature.

**2.** l'empreinte de l'archive, **relevée et consignée** ci-dessus — non pas
comme une vérification, mais pour que la reproductibilité soit possible ;

**3.** le transport TLS vers l'hôte officiel.

## 3. Les affirmations vérifiées **par exécution**

Script joué par `psql --set ON_ERROR_STOP=1 -f`, contre l'amas de test.

| Affirmation | Résultat observé |
|---|---|
| `FETCH FIRST 2 ROWS ONLY` (forme standard) | **2 lignes**, les deux premières |
| `OFFSET 2 ROWS` | **2 lignes**, les deux dernières |
| apostrophe doublée : `'O''Brien'` | relue **`O'Brien`**, longueur **7** — l'encodage n'altère pas la valeur |
| ordre des nuls, défaut en `ASC` | le nul sort **en dernier** |
| `NULLS FIRST` explicite | le nul sort **en premier** |
| `COUNT(*)` contre `COUNT(colonne)` | **4** contre **3** — les deux chiffres diffèrent, comme annoncé |
| `age = NULL` | **accepté** par le serveur et **0 ligne** : jamais vrai |
| `age IS NULL` | **1 ligne** |
| `FROM ELEVES` en majuscules | **4 lignes** — l'identifiant est replié en minuscules |
| `CREATE DOMAIN note AS integer` | accepté |
| contrainte **nommée**, puis supprimée **par son nom** | accepté, les deux |
| **virgules et `AND` en tête de ligne** | du SQL parfaitement valide — la décision **S5** est jouable |
| `EXISTS (SELECT 1 …)` | accepté, résultat juste |
| `IN (SELECT …)` | accepté, même résultat |
| transaction **annulée** | **4 → 0 → 4** : `ROLLBACK` ramène les données |
| `ON_ERROR_STOP=1` | a **arrêté** le script à la première erreur, **code de sortie 3** |

Ce dernier point n'est pas un détail : **sans `ON_ERROR_STOP=1`, `psql`
continue après une erreur et renvoie 0.** La preuve est faite que le réglage
agit, avant d'en dépendre.

## 4. Le défaut que l'exécution a trouvé

La formulation `SQL_IDENTITE` du catalogue proposé était **fausse**, et aucune
lecture de documentation ne l'avait montré :

```
ERROR:  column "id" of relation "eleves" must be declared NOT NULL
        before identity can be added
```

`ALTER TABLE t ALTER COLUMN c ADD GENERATED BY DEFAULT AS IDENTITY` **exige
que la colonne soit déjà `NOT NULL`**. La syntaxe est juste ; l'instruction
échoue quand même. Vérifié : avec `SET NOT NULL` d'abord, elle passe.

**Traitement décidé, et c'est exactement celui de J6 transposé :** A
**n'ajoute pas** le `NOT NULL` à votre place — ce serait choisir à votre place
l'ordre de vos instructions, et la règle 3 l'interdit. Il **informe**, par une
quatorzième information passive :

> **`SQL_IDENTITE_EXIGE_NON_NUL`** — « Cette instruction échouera si la
> colonne n'est pas déjà déclarée `NOT NULL` : PostgreSQL l'exige avant
> d'ajouter une identité. Il faut donc écrire d'abord « Exige que {colonne} de
> la table {table} ne soit jamais nulle. ». SQL-A ne l'ajoute pas à votre
> place : l'ordre de vos instructions vous appartient. »

**C'est le seizième défaut du projet trouvé par une exécution plutôt que par
un test**, et il est arrivé avant la première ligne de moteur. C'était le but
d'installer le serveur **maintenant** plutôt qu'au lot S11.

## 5. Ce que l'installation ne prouve pas

Les 91 formulations proposées n'ont **pas** été jouées — seules les quinze
affirmations du §3 l'ont été, sur des instructions écrites à la main. Le
catalogue reste une **proposition**, et l'exercice de clôture reste à écrire.

Et une limite de l'environnement, inchangée : **une seule machine, un seul
système, un seul serveur**. Rien n'est su de PostgreSQL sur Linux, ni d'un
autre dialecte.

## 6. Comment s'en servir

    node scripts/postgres.mjs     # version et emplacement, en relatif

Le localisateur cherche `CA_PGSQL_HOME`, puis le dossier frère du dépôt, puis
le `PATH`. Il ne renvoie **jamais** de chemin absolu dans ce qu'il imprime, et
l'absence de serveur n'est **pas** une erreur : les lots S0 à S3 doivent
pouvoir avancer sans lui.
